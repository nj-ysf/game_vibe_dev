# 4. GAME CONCEPT

Game title:

**CLOUD WHACK: CHAOS EDITION**

Subtitle:

**45 seconds. 9 holes. One champion.**

The game is inspired by Whack-a-Mole, but all characters are clouds.

Cloud characters randomly pop out of nine holes.

The player must hit friendly clouds to earn points while avoiding dangerous clouds.

Each player gets exactly 45 seconds.

Players compete one after another on the same device.

After each round:

1. The game ends.
2. The final score is displayed.
3. The player enters their personal information.
4. Their score is saved to a CSV file.
5. The leaderboard is updated.
6. The next player can start.

The player with the highest recorded score is the champion.

# 8. SCORING SYSTEM

Use the following base points.

| Character | Points |
|---|---|
| Happy Cloud | +10 |
| Royal Cloud | +30 |
| Storm Cloud | −20 |
| Chaos Cloud | −10 |

## Combo system

Reward consecutive successful hits.

| Consecutive successful hits | Multiplier |
|---|---|
| 0–2 | ×1 |
| 3–4 | ×1.5 |
| 5–9 | ×2 |
| 10+ | ×3 |

Apply the multiplier to the successful hit that reaches the threshold.

Examples:

- Third consecutive Happy Cloud: 15 points.
- Fifth consecutive Happy Cloud: 20 points.
- Tenth consecutive Royal Cloud: 90 points.

A combo resets when:

- The player hits a Storm Cloud.
- The player hits a Chaos Cloud.
- The player misses a friendly cloud.

A missed dangerous cloud does not reset the combo.

Negative points are never multiplied.

Use integer scores and consistent rounding.

The total score must never fall below zero.

### Visual feedback

Show:

- Floating positive and negative points.
- Combo indicators.
- Animated score updates.
- Special Royal Cloud effects.
- New personal record celebration.
- High-score-to-beat indicator.

# 10. PLAYER REGISTRATION AND CSV STORAGE

This requirement is extremely important.

Store all player records in a CSV file:

`backend/data/players.csv`

Use the following columns:

```csv
phone_number,name,filiere,best_score,attempts,updated_at
```

Example:

```csv
phone_number,name,filiere,best_score,attempts,updated_at
0612345678,Youssef Naji,BDCC,850,2,2026-10-21T20:30:00Z
0698765432,Amine,GI,720,1,2026-10-21T20:35:00Z
```

## Unique player identification

Use the normalized phone number as the primary key.

One phone number corresponds to one player record.

### Moroccan phone number normalization

Accept:

- 0612345678
- +212612345678
- 00212612345678
- 0712345678

Normalize numbers to the Moroccan local format.

For example:

`+212612345678` becomes `0612345678`.

Validate that the result is a valid Moroccan mobile number beginning with 06 or 07.

Store phone numbers as strings to preserve leading zeros.

Reject invalid numbers with a clear error message.

## First-time player

If the phone number is not already in the CSV:

1. Create a new record.
2. Save the player's name.
3. Save the filière.
4. Save the final score as best_score.
5. Set attempts to 1.
6. Save the timestamp.

## Returning player

If the phone number already exists:

1. Do not create another row.
2. Increase attempts by one.
3. Compare the new score with the previous best.
4. Keep the highest score.
5. Update the timestamp.
6. Preserve the existing name and filière.

Use:

```python
best_score = max(previous_best_score, new_score)
```

### Example

First attempt:

Youssef: 650 points.

CSV best_score: 650.

Second attempt:

Youssef: 900 points.

CSV best_score: 900.

Third attempt:

Youssef: 400 points.

CSV best_score: 900.

Attempts: 3.

The leaderboard must show Youssef only once.

### New personal record

If a returning player beats their previous score, display:

"NEW PERSONAL BEST!"

Show the previous and new scores.

If the player does not beat their record, display:

"Your best score is still 900!"

# 13. GAME SESSION SECURITY

Avoid blindly trusting client-submitted scores.

At minimum:

- Generate unique game sessions on the backend.
- Enforce one submission per session.
- Validate server-side round duration.
- Reject expired sessions.
- Reject impossible scores.
- Reject malformed requests.
- Rate-limit score submission endpoints.
- Prevent replaying completed sessions.

Prefer implementing server-generated character spawn events and server-side hit validation.

If implementing authoritative gameplay:

1. Generate character types, holes, and appearance times on the server.
2. Associate events with the game session.
3. Record or validate hits against active events.
4. Compute the final score on the server.
5. Use the server-calculated score for CSV storage.

If the full authoritative implementation is too complex for the MVP, implement the simpler session-validated approach, clearly document its anti-cheat limitations, and do not pretend it is cheat-proof.

Keep the project practical for a university stand.
